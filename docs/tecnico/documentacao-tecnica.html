Visão geral e stack

Aplicação web única (Next.js App Router) com PostgreSQL. Cada entidade (Prefeitura, Câmara, autarquia…) é um cliente com dados isolados no banco por Row Level Security.

Ambiente de desenvolvimento

Pré-requisitos

  • Node.js 20+ (testado com 24) e npm.
  • Docker Desktop (Postgres com pgvector, Redis, Silo/MinIO e Mailpit via docker-compose.yml). Sem Docker, npm run db:local sobe um Postgres embutido, mas sem pgvector: a migração ia_documentos falha nele, então use-o só para trabalho que não dependa da IA.
  • Edge ou Chrome instalados (ou npx playwright install chromium) para PDFs e testes E2E.

Primeira execução

cp .env.example .env            # preencha senhas, SESSION_SECRET e CHAVE_CRIPTOGRAFIA
docker compose up -d            # Postgres, Redis, Silo e Mailpit
npm install                     # roda prisma generate no postinstall
npm run db:setup                # cria/atualiza o papel controladoria_app (antes das migrações)
npm run db:deploy               # aplica as migrações
npm run db:seed                 # normas, entidades e usuários de exemplo
npm run demo:popular            # (opcional) dados de demonstração de Catolândia/BA
npm run dev                     # http://localhost:3000
Porta 5432

Se o Postgres embutido (db:local) e o do Docker estiverem ativos ao mesmo tempo, o embutido escuta em 127.0.0.1:5432 e “rouba” as conexões de localhost. Pare um deles antes de rodar migrações.

Multi-entidade e segurança (RLS)

  • Tabelas globais (sem RLS): municipios, clientes, usuarios, sessoes, vinculos_cliente, normas, requisitos. Acesse com db direto.
  • Tabelas por cliente: têm cliente_id, ENABLE + FORCE ROW LEVEL SECURITY e a política isolamento_cliente (cliente_id = app_cliente_id()). Acesse sempre via comCliente(ctx, tx => …), que abre transação e faz set_config de app.cliente_id, app.usuario_id e app.perfil.
  • Satélite: políticas restritivas (app_eh_satelite(), app_unidades_satelite()) limitam o perfil às demandas das suas unidades; documentos internos (auditorias, alertas, relatório anual e seu texto padrão) recusam leitura e gravação.
  • A aplicação conecta com controladoria_app (NOBYPASSRLS). npm run test:rls verifica o isolamento.

Checklist para uma tabela nova por cliente

  1. Modelo no schema.prisma com clienteId e relação com Cliente (onDelete: Cascade).
  2. Migração com ENABLE/FORCE ROW LEVEL SECURITY, política isolamento_cliente e, se for interna, a política restritiva do satélite; GRANT condicional ao papel (bloco DO $$ … $$), como em 20261008120000_painel_alertas_modelo_anual.
  3. CHECKs para JSON (jsonb_typeof(...) = 'object') e faixas.
  4. Casos em testar-rls.ts ou no teste do módulo (satélite e outro cliente não leem).

Autenticação e sessão

  • src/proxy.ts (o antigo middleware) só verifica a presença/assinatura do cookie e redireciona para /login?voltar=…. A validação real da sessão é feita no servidor, no banco.
  • src/lib/auth/dal.ts: obterSessao (cacheada por requisição), exigirUsuario, obterContexto, exigirContexto(perfis). Toda página e Server Action começa por um deles.
  • Link do município (/m/<slug>): a sessão guarda municipioAcesso e só alcança as entidades daquele município (admins HorizonAJ ficam livres).
  • Tentativas de login são limitadas (src/lib/limite.ts) e registradas na trilha global.

Banco de dados e migrações

  • Migrações em prisma/migrations/AAAAMMDDHHMMSS_nome/migration.sql; políticas RLS, CHECKs e GRANTs são escritos à mão no mesmo arquivo.
  • Desenvolvimento: npm run db:migrate (cria) · Produção: npm run db:deploy (aplica). Depois de mudar o schema: npm run db:generate.
  • UUID v7 (@default(uuid(7))), datas timestamptz(3), nomes de colunas em snake_case via @map.

Dívida e resultado primário para a Câmara (v1.1)

Dívida consolidada e resultado primário são indicadores do ente, publicados pelo Executivo. Para clientes do Legislativo, coletarSiconfi agora lê o RGF Anexo 2 (com co_poder=E) e o RREO Anexo 6 a partir das entregas da Prefeitura, com o sufixo “— Executivo municipal” na referência. A despesa com pessoal continua sendo a do próprio Poder.

Alertas fiscais (lib/integracoes/alertas-fiscais.ts)

Funções puras que transformam a coleta do SICONFI em uma lista ordenada por gravidade (EXCEDIDO → PRUDENCIAL → ALERTA → INFO):

  • pessoal: faixa da LRF ≠ regular (limites em lrf.ts: alerta 90%, prudencial 95%, máximo 54%/6%);
  • divida: DCL/RCL ≥ 108% (alerta) ou > 120%;
  • entregas: demonstrativos pendentes (prudencial se mais de dois);
  • coleta: sem código IBGE, coleta falha ou dados com mais de 40 dias.

Cada alerta traz registrar, um link para /alertas/nova com título, descrição (com base legal) e probabilidade/impacto sugeridos. A lista é exibida pelo componente components/alertas/alertas-fiscais.tsx no Painel, em Alertas e em Dados externos.

Painel personalizável e preferências

Catálogo de blocos

lib/painel/blocos.ts define os blocos (id, título, descrição e página de origem). A ordem do catálogo é a ordem de exibição. Para criar um bloco: adicione-o ao catálogo, ao mapa de ícones/largura em painel/page.tsx, ao switch de conteúdo e, se precisar de dados novos, a resumoPainel.

Preferências (usuarios.preferencias)

{
  "painel":         { "ocultos": ["unidades"], "recolhidos": ["indices"] },
  "dados-externos": { "recolhidos": ["fontes"] },
  "alertas":        { "recolhidos": ["painel"] }
}
  • Esquema e leitura tolerante em preferencias-esquema.ts (zod; ids [a-z0-9-], até 50). Guardamos ocultos (e não visíveis) para que blocos novos apareçam por padrão.
  • gravarPreferencia() faz o merge numa única instrução SQL (preferencias || jsonb_build_object(...)), sem ler antes: cliques rápidos ou outra aba não sobrescrevem os demais campos.
  • Server Actions em app/actions/preferencias.ts: salvarRecolhidos(pagina, ids) (sem revalidar) e salvarBlocosPainel(visiveis) (revalida /painel).

Componente components/recolhivel.tsx

  • ProvedorRecolhiveis recebe a página e os recolhidos iniciais (lidos no servidor, sem “piscar”) e grava as mudanças com atraso de 400 ms.
  • BlocoRecolhivel: cartão com cabeçalho-botão (aria-expanded/aria-controls), resumo quando recolhido e conteúdo renderizado no servidor (apenas hidden).
  • AlternarTodos: “Recolher tudo / Expandir tudo”.
  • Para usar em outra página, inclua o nome em PAGINAS_PREFERENCIA.

Menu sem barra de rolagem

O menu lateral foi compactado e as áreas que ainda podem rolar em telas baixas usam a utilidade sem-barra-rolagem (globals.css, @utility); os temas “topo” e “faixas” quebram linha em vez de rolar na horizontal. npm run test:e2e:painel verifica os seis temas em 1366×768 e 1366×650.

Relatórios em PDF e Relatório Anual

  • Cada relatório tem um montador em lib/relatorios/<tipo>.ts que devolve HTML (template html`` com escape automático), cabeçalho e rodapé; as rotas relatorios/pdf/*/route.ts chamam responderPdf, que gera o PDF e registra a emissão na trilha.
  • O satélite é recusado em exigirControle(), além da RLS.

Texto padrão do Relatório Anual (v1.1)

Resolução de cada uma das seis seções (anual-padrao.ts → secoesEfetivas):

  1. texto do exercício (relatorios_anuais.secoes);
  2. texto padrão do cliente (modelos_relatorio_anual.secoes);
  3. texto-base do sistema (TEXTO_BASE_ANUAL).
  • Ao salvar um exercício, somentePersonalizadas() grava só as seções diferentes do padrão (comparação normalizando quebras de linha e espaços nas pontas). Assim, as demais seguem o padrão inclusive quando ele mudar.
  • Ao salvar o padrão, somenteDiferentesDoSistema() não grava seções idênticas ao texto-base.
  • Variáveis {entidade}, {municipio}, {uf}, {ano}, {ano_seguinte} são substituídas só na emissão (aplicarVariaveis); variáveis desconhecidas ficam como estão.
  • Telas: /relatorios/anual/padrao (texto padrão + seletor de exercício) e /relatorios/anual/[ano]; o formulário form-relatorio-anual.tsx serve aos dois modos e mostra, por seção, se segue a referência.
  • Trilha: relatorio_anual.salvo (com secoesPersonalizadas) e relatorio_anual.padrao_salvo.

IA, e-mails e rotinas agendadas

  • IA: configuração por cliente/global em /admin/ia (chaves cifradas), mascaramento de dados pessoais antes do envio, citações obrigatórias e revisão humana das sugestões. IA_PROVEDOR=falso nos testes.
  • E-mails: notificações de demandas (lib/email/); em desenvolvimento, caixa do Mailpit em http://localhost:8025.
  • Cron (ver docs/implantacao-vps.md): npm run lembretes:prazo (lembretes de prazo) e npm run integracoes:sincronizar (dados externos, diário).

Testes

Os testes são scripts tsx com verificações explícitas (saída “OK/FALHA” e código de saída ≠ 0 em falha). Os que importam módulos server-only rodam com --conditions=react-server (já configurado no package.json). Requerem migrações + seed; os E2E requerem também npm run dev.

Dados de teste

Os testes que dependem do seed escolhem os clientes mais antigos (ORDER BY criado_em), porque o banco pode conter também os dados de demonstração. Os testes que alteram registros (tema, preferências, texto padrão) restauram o estado original no finally.

Convenções de código

  • Código, rotas, tabelas e mensagens em português; nomes descritivos (exigirContexto, calcularAlertasFiscais).
  • Páginas são Server Components; interatividade em componentes "use client" pequenos. Mutação por Server Action que começa com exigirContexto/exigirUsuario, valida com zod, grava via comCliente, registra na trilha e chama revalidatePath.
  • Retorno padrão das actions: EstadoAcao ({ ok, erro, mensagem }); mensagens de erro amigáveis via mensagemDeErro.
  • Estados vazios, de carregamento e de erro explícitos nas telas; acessibilidade (rótulos, aria-*, foco visível).
  • Rótulos exibidos ficam em lib/rotulos.ts; regras puras em módulos sem dependência de servidor, para serem testadas sem banco.
  • Formatação: Prettier com largura de linha 150 (padrão dos arquivos existentes).
